# GloraX — тестирование знаний проектов

Flask-приложение с настоящим HTTP-сбором каталога GloraX, PostgreSQL, версионными фактами и вопросами, серверными попытками, административной панелью и отдельным worker. Платный LLM API не нужен. Это развитие исходной заготовки; SQLite-файл не удалён и не используется как production-хранилище.

## Что работает

- Сотрудник выбирает проект, вводит ФИО и необязательный код. Без кода создаётся отдельный участник, одинаковые имена не объединяются. Код хранится как HMAC и связывает повторные попытки; знание кода не является корпоративной аутентификацией.
- На старте фиксируются полный состав вопросов, версии, порядок вопросов и независимое перемешивание вариантов. Ответы получают непрозрачные UUID. API отдаёт только текущий вопрос.
- PostgreSQL блокирует строку попытки при выдаче/ответе; время берётся из `clock_timestamp()`. Первый GET открывает вопрос на 20 секунд. Повторный ответ не меняет первый ответ и не увеличивает балл. Ограничения и триггеры БД защищают историю и дедлайны.
- Worker отдельно обрабатывает сбор и просрочки. Даже при длительном сетевом запросе второй процесс фиксирует таймауты. Неоткрытый следующий вопрос ещё не тратит время. Бездействие прерывает попытку; процент считается от всех назначенных вопросов.
- Администратор видит участников, фильтры, поиск, каждый ответ, CSV, статистику, источники, версии, конфликты и журнал действий. Можно редактировать факты/вопросы, архивировать, публиковать, настраивать количество/темы/сроки/разбор.
- Импорт JSON: экспорт фактов с JSON Schema и готовым промптом → предпросмотр → выбранные записи → черновики. Конфликт `external_id` требует явного разрешения обновления. Варианты формируются из фактов сервером.

## Ограничения источника и проверок

См. [отчёт источников](docs/SOURCE_REPORT.md) и [отчёт проверок](docs/VERIFICATION.md). Нет выдуманных цен, максимумов или запасных ответов. Полного разрешённого обхода предложений квартир нет: диапазоны цен автоматически не публикуются. Публичные «от» сохранены отдельно и требуют проверки условий акций. Изображения/PDF не интерпретируются как подтверждённые факты; ссылки и кандидаты показаны для проверки. Свободный текст, признаки наличия, планы инфраструктуры и экспертные оценки не публикуются автоматически. У части категорий может не оказаться четырёх сопоставимых значений — генератор объясняет пропуск.

Автоматические вопросы используют только известные шаблоны и однозначные скалярные характеристики: географию, площади по типу/комнатности, число корпусов, этажность, кварталы сдачи, транспорт и другие подходящие ключи. Шаблон цены существует, но требует подтверждённой цены, типа, валюты, условий, даты и полноты соответствующей выборки. Отсутствие признака в тексте никогда не трактуется как отрицание. Статус `is_exclusive` у ручного факта — ответственное утверждение редактора о единственности значения внутри области, а не автоматическое доказательство для произвольного текста.

## Локальный запуск

Python 3.13+ и PostgreSQL 16. Проверено локально на Python 3.14.7 / PostgreSQL 16.15; CI и Render используют Python 3.13. Рабочая директория должна быть корнем проекта.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
python -c 'import secrets; print(secrets.token_hex(32))'
```

Запишите сгенерированное значение в `SECRET_KEY` внутри `.env`. Файл игнорируется Git, пароль администратора по умолчанию отсутствует.

Локальную БД можно поднять через `docker compose up -d db`. Это только локальная конфигурация с явно учебным паролем. Тогда `DATABASE_URL` в `.env`:

```dotenv
APP_ENV=development
DATABASE_URL=postgresql+psycopg://glorax:local-development-only@127.0.0.1:5432/glorax
```

Либо используйте свою локальную PostgreSQL. SQLite в режиме разработки допустим для просмотра пустого интерфейса, но не подходит для проверки очереди/конкурентности и не используется в основных тестах.

```bash
python scripts/migrate.py
flask --app app create-admin --username YOUR_LOGIN
flask --app app enqueue-refresh
python -m glorax.worker
```

`create-admin` интерактивно запрашивает пароль дважды (не менее 12 символов). В другом терминале:

```bash
source .venv/bin/activate
flask --app app run --port 5001
```

Откройте `http://127.0.0.1:5001`, вход — `/admin/login`. Ни импорт приложения, ни открытие главной страницы не запускают сбор. Для обработки одного задания: `python -m glorax.worker --once`.

В текущей рабочей папке уже создана локальная `.env` со случайным секретом и подключением к отдельной тестовой PostgreSQL на порту 55432. В `glorax_local` перенесена старая база и загружен реальный каталог; администратора создайте командой выше. Локальный кластер расположен в игнорируемом `instance/pg-test`; это удобство текущей машины, не схема развёртывания.

## Перенос старой SQLite

Сначала остановите старое приложение, чтобы получить неподвижный источник. Используйте новую пустую целевую БД после миграций. Никогда не направляйте Alembic на старую SQLite: таблицы старой схемы имеют совпадающие имена.

```bash
python scripts/migrate.py
flask --app app import-legacy /absolute/path/instance/glorax.db --backup-dir /secure/persistent/backups
```

Команда открывает источник только для чтения, делает согласованную резервную копию SQLite через backup API, вычисляет SHA-256, сохраняет исходные записи и сопоставление ID. Повторный импорт того же содержимого ничего не добавляет. Изменённый файл имеет другую контрольную сумму и считается отдельным источником; не импортируйте несколько снимков одной старой БД как независимые базы без анализа дубликатов.

Старые проекты отключены, факты имеют `legacy_unverified`, вопросы — `needs_review`. Они не подмешиваются к проверенному каталогу и автоматически не объединяются по названиям. В админке они доступны для проверки. Старые попытки не имели снимков, размера/порядка теста и времени завершения: сохранены исходный балл и все доступные логи, процент обозначен неизвестным. Даже если вопрос с тем же числовым ID существует сейчас в старой таблице, это не доказательство прежней формулировки — она не реконструируется.

Изначальный файл текущего проекта содержит 29 проектов, 87 вопросов, 4 попытки и 12 логов ответов. Резервные копии лежат в `backups/`, исходник остаётся `instance/glorax.db`. Оба каталога исключены из Git. В этой рабочей папке изначально не было `.git`; перед публикацией создайте/подключите Git-репозиторий и проверьте состав индекса. `.gitignore` не удаляет уже отслеживаемые файлы — если БД ранее попала в другой Git-репозиторий, исключите её из индекса и отдельно решите вопрос очистки истории.

## Aiven PostgreSQL

Создайте или выберите PostgreSQL в Aiven самостоятельно; эта работа не создаёт платных ресурсов. Для production используйте стабильное DNS-имя Aiven, не IP. В Overview скачайте CA проекта. [Документация Aiven](https://aiven.io/docs/platform/concepts/tls-ssl-certificates) указывает: `require` шифрует канал, но не проверяет сертификат; `verify-full` дополнительно проверяет цепочку и имя хоста. Приложение требует именно `verify-full` и существующий CA-файл.

```dotenv
APP_ENV=production
SECRET_KEY=<случайный секрет не менее 32 символов>
DATABASE_URL=postgresql+psycopg://<user>:<urlencoded-password>@<service-host>:<port>/<database>?sslmode=verify-full
PGSSLROOTCERT=/etc/secrets/aiven-ca.pem
DB_POOL_SIZE=3
DB_MAX_OVERFLOW=1
TRUST_PROXY=1
DISPLAY_TIMEZONE=Europe/Moscow
WORKER_LEASE_SECONDS=600
WORKER_MAX_ATTEMPTS=3
```

Не помещайте реальные значения в README, YAML, Git или логи. URL-кодируйте специальные символы пароля. CA добавляется как **Secret File** `aiven-ca.pem` отдельно к web и worker. При ротации сертификата обновите bundle на обоих сервисах. Если сертификат/имя не проходят проверку, исправьте host/CA, не ослабляйте TLS.

Пул указан на процесс: два Gunicorn-процесса × максимум 4 соединения + два процесса worker × 2 = до 12 рабочих соединений, плюс миграции/обслуживание. Сверьте это с лимитом вашего Aiven-тарифа и уменьшите параметры, если нужно. Worker может держать одно соединение во время публикации; между заданиями сессии освобождаются. Настройте доступ сети Aiven под исходящие адреса выбранного Render-региона.

## Render

[render.yaml](render.yaml) описывает **платные** web и background worker, внешнюю Aiven и ни одной дополнительной Render PostgreSQL/Redis. Автоматическое развёртывание отключено. Конфигурацию не применяли к аккаунту пользователя.

1. Подключите Git-репозиторий к Blueprint Render.
2. Заполните одинаковые `SECRET_KEY` и `DATABASE_URL` для двух сервисов. Добавьте CA Secret File каждому сервису. Проверьте тарифы и лимиты до подтверждения создания.
3. Web: build `pip install -r requirements.txt`, pre-deploy `python scripts/migrate.py`, start Gunicorn из YAML, health `/healthz`.
4. Первый запуск: сначала дождитесь успешной миграции web, затем запускайте worker. У worker нет pre-deploy миграции, чтобы не запускать её параллельно.
5. В защищённом shell создайте администратора и выполните `flask --app app enqueue-refresh`. Дальше обновления запускаются из админки. Перенос SQLite лучше выполнить с локальной машины прямо в Aiven после миграций; резервную копию храните вне Render.

[Render pre-deploy](https://render.com/docs/deploys#pre-deploy-command) доступен платным web/private/worker-сервисам. Если hook недоступен, выполните **один** `python scripts/migrate.py` с доверенной машины/одноразового job с тем же кодом, CA и окружением до запуска новой версии; не вставляйте миграцию в Gunicorn startup. Скрипт сериализует миграции advisory-lock PostgreSQL. При обычных обновлениях миграции должны оставаться совместимыми со старой версией; несовместимое изменение требует остановки web/worker и окна обслуживания.

[Render Free](https://render.com/docs/free) не поддерживает бесплатные background workers; free web засыпает и не рекомендуется для production. [Файловая система Render эфемерна](https://render.com/docs/deploys#ephemeral-filesystem): постоянные данные, исходные материалы, задания и ответы живут в Aiven. CA приходит из secret file, а не создаётся при сборке. Тариф Aiven выбирается отдельно, бесплатная работа всей конфигурации не обещается. Официальные страницы проверены 27.09.2026.

## Обновления, сбои и восстановление

Очередь находится в `job`: уникальный `active_key` препятствует двум одновременным заданиям обновления. Захват — `FOR UPDATE SKIP LOCKED`, lease и fencing token. Потерянное задание после истечения lease восстанавливается, повторы ограничены. Невалидный/неполный обход не меняет опубликованный снимок. Весь новый снимок, версии фактов и генерация вопросов публикуются одной транзакцией. Старые значения не обнуляются, исчезнувшие проекты не удаляются.

В админке смотрите этап, счётчики, сообщения источника и JSON-отчёт: новые/изменившиеся проекты, конфликты, пропуски генерации. После исчерпания автоматических повторов доступна кнопка «Повторить сбор». При изменении структуры сайта исправьте парсер и добавьте сохранённый образец в тесты. Если сайт ограничивает доступ/robots, не обходите защиту; оставьте последнюю версию с её исходными датами.

При ручном изменении создаётся версия с автором и новый снимок. Сбор не перезаписывает ручное значение; противоречащий кандидат сохраняется в истории факта и отчёте конфликтов. Зависимые вопросы отправляются на повторную проверку. Завершённые и текущие попытки читают собственные снимки. Для повторной генерации после редакторских правок: `flask --app app generate-questions`.

Экспорт фактов без сотрудников: `/admin/dataset.json` или `flask --app app export-dataset /secure/output/dataset.json`. Сроки актуальности и число вопросов настраиваются в админке. Изменение срока применяется к новым версиям, не переписывая старые даты.

## Резервное копирование

Используйте резервные копии и доступные вашему тарифу возможности восстановления Aiven. Дополнительно делайте логический `pg_dump --format=custom --file=/secure/backups/glorax.dump` с PostgreSQL-переменными окружения (`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGSSLMODE=verify-full`, `PGSSLROOTCERT`) из secret manager/защищённого окружения. Не передавайте пароль аргументом процесса. Храните зашифрованную копию вне Render с ограниченным доступом: база содержит ФИО.

Восстанавливайте сначала в отдельную пустую PostgreSQL: `pg_restore --no-owner --no-acl --dbname=<target-db> /secure/backups/glorax.dump` с аналогичными TLS-настройками. Проверьте количество записей, Alembic revision, старую попытку и полный тест; лишь затем переключайте web/worker. Восстановление поверх рабочей базы, удаление истории или отключение защитных триггеров не являются штатной процедурой. Триггеры сохраняются в dump; при restore в пустую базу post-data триггеры устанавливаются после загрузки строк.

## Проверки

Тесты создают отдельную временную схему внутри выделенной тестовой PostgreSQL и применяют настоящие Alembic-миграции; рабочие таблицы не очищают. Пользователю тестовой БД нужно право `CREATE SCHEMA`.

```bash
export TEST_DATABASE_URL=postgresql+psycopg://<test-user>:<test-password>@127.0.0.1:5432/glorax_test
python -m pytest -q
```

Реальный браузер (дополнительная зависимость, не нужна production):

```bash
pip install 'playwright>=1.50,<2'
python -m playwright install chromium
RUN_BROWSER_TESTS=1 python -m pytest tests/test_browser.py -q
```

Живой сбор без записи в БД:

```bash
python -m glorax.parser --output /secure/output/live-source.json
```

Образцы `tests/fixtures/*.gz` получены с публичных страниц; сетевые тесты не подменяют их выдуманной разметкой. Для граничных случаев/конкурентности применяются явно тестовые данные `tests/conftest.py`; в приложение они не загружаются. Основной браузерный тест проверяет мобильный экран 390×844 и desktop 1366×900, перезагрузку, полный путь сотрудника и просмотр ответов администратором. Скриншоты остаются в игнорируемом `reports/browser/`.

## Модули

`glorax/config.py` — окружение/TLS; `models.py` — схема; `parser.py` — публичные источники; `facts.py` — снимки и правки; `questions.py` — формальные шаблоны; `importing.py` — JSON Schema/импорт; `attempts.py` — серверная попытка; `auth.py`/`admin.py` — доступ и админка; `jobs.py`/`worker.py` — очередь и обслуживание; `legacy.py` — перенос; `migrations/` — Alembic. Интерфейс — Jinja и локальные CSS/JS, без обязательного CDN. Все административные формы и JSON API защищены CSRF, браузерные сессии — HttpOnly/SameSite, production — Secure, вход ограничен по IP в общей БД.
